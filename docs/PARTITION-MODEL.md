# 分区模型 —— CogniCustos 的数据架构

> **状态**：设计定稿（讨论产出）。本文只定**规则与边界**，不定表结构。
> **日期**：2026-11-24
> **来源**：设计讨论，非代码现状。代码实现情况见 §10。
> **读法**：每条都标了状态——**【已定】** 讨论中明确确认；**【倾向】** 有明确方向但未最终拍板；**【待定】** 尚未决定。不要把【倾向】当成承诺。

---

## 0. 一句话

系统的组织原则是「**分区 + 通道**」。数据、对话、权限、执行都是同一个模式的实例：**边界由确定性代码把守，模型只在区内自由行动。**

---

## 1. 分区

### 1.1 分区的定义

一个「区」要同时满足三条，否则它只是个文件夹：

1. **封闭** —— 区内内容默认出不去；
2. **单向** —— 流动有方向，逆向需要更强的授权；
3. **可追溯** —— 每次跨界留下记录。

分区不是物理隔离。它不要求分文件、分库、分进程——**它的强度取决于「有没有绕过通道的入口」**。所以首选做法永远是**让那条路径根本不存在**，而不是存在之后再补检查。

### 1.2 四个区

```
外部世界：邮件 / 社交消息 / 学校官网 / 课件 PDF / 校历课表
   │  ① 抓取与导入（抓取器写入）
   ▼
【原始数据库】信息侧 · 低可信 · 只增不改
   │  ② AI 读取、提炼、概括
   ▼
【沙箱】加工与待确认区 · AI 自由写
   │  ③ 用户确认（应用执行，不是模型执行）
   ├──────────────────►【主数据库】事实侧 · 权威（课程 / 校历事实 / 任务 / 日程）
   └──────────────────►【知识库】  语义侧 · 权威（资料 / 摘要 / 可检索）
```

| 区 | 内容 | 谁可写 | 可信度 | 默认可被引用 | 生命周期 |
|---|---|---|---|---|---|
| **原始数据库** | 抓来的原件：邮件、网页、PDF、校历、消息 | 抓取器（系统） | 低（未判断） | 否（仅供发现） | 永久保留，用户可设定期限清理 |
| **沙箱** | AI 的草稿、推理、待确认提议 | AI 自由写；用户可读、可改（视为干预） | 低，允许含幻觉 | 否 | 可覆盖，条目化后按需归档 |
| **主数据库** | 课程、校历事实、任务、日程 | 用户直接；AI 只能提议 | 权威 | 是 | 永久，可撤回 |
| **知识库** | 已确认的原始资料、摘要 | 用户直接；AI 只能提议 | 权威 | 是 | 永久，可撤回 |

**归属澄清【已定】**：**原始数据库属于信息侧**，可视为知识库那一侧的低可信层；**沙箱是独立的加工与待确认区**，不属于知识库。两个"数据库"分属结构化的两侧，这正是命名歧义的来源。

### 1.3 通道（唯一合法的跨界方式）

| 从 → 到 | 触发 | 执行者 | 留痕 |
|---|---|---|---|
| 外部 → 原始 | 抓取 / 导入 | 抓取器（代码） | 是 |
| 原始 → 沙箱 | AI 读取、提炼、生成概括 | 模型（只读） | 是（读了什么） |
| 沙箱 → 主数据库 | 用户确认 | **应用（代码）** | 是 |
| 沙箱 → 知识库 | 用户确认 | **应用（代码）** | 是 |
| 原始 → 知识库 | 用户确认收录 | **应用（代码）** | 是 |

**没有"模型直接写权威区"这条通道。** 这不是策略，是结构：AI 的工具集里不存在这样的函数。

### 1.4 一条材料可以有两个落点【已定】

校历是标准例子：

- **校历文档本身** → 知识库（可检索、可引用）；
- **从校历里提炼出的事实**（假期区间、考试周、学期起止）→ 主数据库。

由此：**一条提议 = 一个变更集**，可以包含多个落点、一张确认卡、一次确认、一个事务。

## 2. 边界由确定性组件把守

> **原则：边界必须由确定性的组件执行，概率性的组件只能住在边界里面。**
> 理由不是"保证绝对安全"，而是**成本**——下列四件事是"少写一段代码"换来的，不需要任何额外机制。

### 2.1 结构性关闭（默认就是关的）

1. AI 的工具集里**没有**写主数据库的函数；
2. 原始区只有「追加」，**没有**「修改」；
3. 确认由**应用**执行，不由模型执行（模型只提议）；
4. 删除默认**软删**，物理回收需要显式操作。

### 2.2 明确不做【已定】

本项目是私人自用 + 公益开源的课程项目，目标**不是**"防备有意的用户"，而是"**正常使用下不出现异常权限泄露**"。因此不做：

- 对话级能力令牌 / 权限引擎；
- 跨区全链路强制审计表；
- 判定对话返回结果的 schema 强校验（用提示词 + 结构约定即可）；
- 数据库加密（对抗本地物理访问者）；凭证加密另议，见 §8。

### 2.3 窄工具面

工具少 → 变更类型少 → 执行器少 → 出错面小。这是同一个最小化在三处的同一次表达。推论：**提议的 payload 应按目标定型**，不是通用 JSON blob——畸形的提议应当**在提议时**失败并回话，而不是等到用户点了确认、应用器解析时才崩。

## 3. 可见性阶梯与三种同意

### 3.1 五档可见性【倾向】

| 档位 | 内容 | 能被检索到 | 能读细节 | 能被引用 |
|---|---|---|---|---|
| R0 原始·原件 | 刚进来的字节 | 否 | AI（判定用途） | 否 |
| R1 原始·概括 | 入库时自动生成的一段概括 | **是（仅概括）** | 否 | 否 |
| S 沙箱 | AI 草稿 / 待确认提议 | 部分（卡片） | AI | 否 |
| K 知识库 | 已确认资料 | 是 | 是 | 是 |
| M 主数据库 | 已确认事实 | 是 | 是 | 是 |

### 3.2 判定对话的隔离【已定】

未确认的内容不进入主对话。它进入一个**独立的判定对话**：该对话可以读取未确认材料，判断是否与用户当前问题相关，然后**只回传裁决与句柄**（相关/不相关、类别、引用 id），不回传正文。主对话据此询问用户"发现一份相关材料，要确认后使用吗？"。

推论：**上下文边界 = 信任边界。**

| 来源 | 进主对话？ | 路径 |
|---|---|---|
| 已确认（K / M） | 可以 | 检索直取，进了就当事实用 |
| 未确认（R0 / R1） | 不可以 | 只能进判定对话，回裁决与句柄 |

### 3.3 三种同意必须分开【已定】

| 同意 | 持续多久 | 是否改变数据 | 典型说法 |
|---|---|---|---|
| **发现** | 永久（无需授权） | 否 | "我这儿可能有相关材料，没确认" |
| **读取** | 单次 / 本次对话 | 否 | "你读一下细节，帮我判断要不要收" |
| **确认** | 长期 | **是**（升格为 K / M） | "确认收录" |

风险量级完全不同：读取泄露的是**这一次**，确认泄露的是**永久**。

### 3.4 分区约束的是模型，不是人【已定】

**用户看 = 不跨界；模型读 = 跨界。** 用户要看未确认材料的细节，应用直接把原文渲染给他看即可，全程零模型参与——这永远是比"让模型转述"更安全、也更省的选择。

同理，用户直接改沙箱不算越权：**风险不在权限，而在于它会污染 AI 的记忆**，所以标记的是"干预"，不是"违规"。

## 4. 决策分工

### 4.1 AI 管内容，架构管门槛【已定】

| | 归 AI | 归架构（代码 / 开发者） |
|---|---|---|
| 内容 | 这是什么、属于哪个区、该不该提议、提什么 | — |
| 不确定性 | 哪里没把握、哪里前后矛盾、要问什么 | — |
| 门槛 | — | 要不要人签字、卡片长什么样 |
| 节奏 | — | 多久提醒一次、几条算多、如何防止确认疲劳 |

### 4.2 模型可以提议内容，不能提议门槛【倾向】

**确认级别是「变更类型」的属性，在代码里声明，模型无权影响。**

判定依据必须是结构性事实，而非模型对用户感受的估计：

- 能不能一条命令撤销；
- 影响几张表、几条记录；
- 是否跨越分区（原始 → 确认）；
- 是否触碰已确认数据。

如果模型能影响门槛，门槛就不再是架构，会退回成"提示词自觉"。

### 4.3 不让 AI 管"省心"【已定】

**"省心不省心"是架构的后果，不是 AI 的决策变量。** AI 的任何决策都不应涉及"这会不会让用户省心/不省心"。

这条同时挡掉一个副作用：一个被要求"优化体验"的模型，最理性的做法是少报问题、软化坏消息、跳过会引发追问的环节——即讨好。把"省心"从它的决策变量里拿掉，等于顺手堵住这条路径。

它只负责把事实和疑问摆出来；烦不烦、要不要打断、怎么呈现，是架构的事，也是用户的事。

## 5. 时序架构【已定】

### 5.1 只给事实，不给指令

系统按 2 / 4 / 6 / 8 分钟向 AI 注入**已进行的时间**，**不告诉它该不该停**。理由是"该不该停"只有模型结合上下文才判得出来；写成固定指令等于用一句话替它做判断，还会和用户当下的要求（"帮我排完这一周"）打架。

措辞必须是**传感器读数**，不是建议：

- 合适：`[已进行 06:12 · 3 次工具调用 · 2 条待确认]`
- 不合适：`[已进行 6 分钟，建议你停下来汇报]`

连标签都不要叫"提醒"——"提醒"这个词本身就暗示"该行动了"，等于把策略偷偷塞回去。

### 5.2 计时范围

只约束「**当前对话里模型的连续自主行动**」。后台作业（索引、批量摘要、清理）**不计入**，它们报告的是进度，不是时长。这两件事长得像，性质完全不同。

### 5.3 是否升级为指令，由测试决定

不预先加"该停"的指令。出现下列三种可观察失败时，再按方向补提示词：

| 观察到的现象 | 说明什么 | 该补什么 |
|---|---|---|
| 报到 6 分钟仍无限行动 | 数字被当成无害背景 | 补"该停"的许可，不是补强制 |
| 一到 2 分钟就草率收尾 | 数字被读成了命令 | 补"何时停止由你判断"（方向相反） |
| 报到后仍重复同一工具、同一失败 | 这不是该停，是卡住了 | 需要"换策略"信号，不是时间 |

### 5.4 待回应队列【已定】

"该问就问"的问题如果只活在对话里，会随对话结束而死掉。沙箱里应积两类条目：

1. **用户的干预**：用户手改了沙箱（标记为干预，不问责），AI 需在下一轮解释或修正；
2. **AI 的疑问**：发现矛盾、不确定、需要用户一句话才能继续的事。

两者性质相同——"悬而未决、等人给一句话"。好处是它把"以人决策为主"变成可运营的：打开就能看到还有几条没处理，而不是靠翻聊天记录。

> 提示词负责"问得体面"，架构负责"不可能忘记"。

## 6. 数据层必须满足的约束

不规定表结构，但下列规则约束将来的表结构。

1. **每一行都能回答四件事**：属于哪个区、谁写的、从哪来、以什么形式跨界（原件？概括？提炼出的事实？）。第三项现在完全没有——而溯源、标注幻觉、事后追责都依赖它。
2. **提议 = 变更集**：可含多个落点，一张卡、一次确认、一个事务（整批批准或整批驳回，MVP 不做部分批准【待定】）。
3. **解析失败不猜**：认不出的输入必须报错回话，禁止静默降级成某个默认值——那是意外错误进入权威库的主要通道。
4. **每个变更类型必须有人话渲染**：渲染的必须是即将真正写入的那几个字段，不是摘要版。看不懂的卡片等于自动批准。
5. **重复提议可识别**：模型会重试、会重复提同一件事；同一目标的相同 payload 应能被识别为重复，而不是变成两条记录。
6. **原始区内容寻址、只增不改**：同一文件自动去重；换更好的解析器可以重跑；删除原始条目**不影响**已确认的事实（只标记来源"原件已删除"）。
7. **类型与区间在提取时确定**：一条事实被提炼出来时就必须带上类型和日期区间（假日 / 考试周 / 学期起止 / DDL / 上课），否则视图层只能猜。
8. **时间保留原始表达**：模型可能说 "Friday"，也可能会说 "2026-12-27"。原始文本与解析值都存，解析失败时留原文并标记待澄清。

## 7. 威胁模型与已知会漏的地方

### 7.1 威胁模型【已定】

要防的是**正常使用下的异常**：AI 积极过头、糊了、顺着上下文走偏、被材料里的指令带跑。
**不防**：有意的用户专门找漏洞绕过限制。这不是本项目要解决的问题。

### 7.2 已知会漏（如实列出）

1. **提示词约束会被长上下文稀释**——会话越长，AI 越可能忘记停、忘记问。
2. **判定器可能过度解读**，把不相关判成相关，导致多余询问。
3. **确认疲劳**——最现实的一种失效：不是 AI 越权，而是用户不再看卡片、直接确认。
4. **抓入的材料可能含指令**（注入）。它能影响"提什么"，但改不了数据——因为数据由应用写入。
5. **本地小模型的概括质量有限**，可能导致相关材料被漏检。
6. **保留策略配错会误删**——靠默认软删兜住。
7. **沙箱整节覆盖可能丢失早期判断**——需要条目化 + 时间戳。
8. **没有静态数据加密**：能读磁盘的人就能读数据。

## 8. 待定事项

1. **知识库引擎**：提案文档写的是 LanceDB，但它是 Rust 核心、无官方 .NET SDK，与"无服务器、单进程"的卖点冲突。**倾向**改为「SQLite 单文件 + FTS5 关键词 + 向量列暴力余弦」的混合检索，LanceDB 降级为未来工作（提案文档里"每个候选都可替换"的表述已留口子）。未拍板。
2. **一次行动的计时起点**：用户发出消息，还是模型首次调用工具？**倾向**前者（用户感知的是从回车到拿到答案的时间）。
3. **变更类型的门槛分级**：哪些类型"上线前签字"，哪些"上线后可见可撤销"（见 §4.2）。规则本身【倾向】，具体清单未定。
4. **时间账本是否落盘**：若要展示"这周 AI 替你处理了多久"，需要一条持久记录；若不做，运行时内存足够。
5. **凭证加密边界**：提案承诺凭证存"encrypted local storage"，当前 settings.json 是明文。跨平台方案未定。
6. **变更集能否部分批准**：MVP 倾向整批，需要确认。

## 9. 术语

| 中文 | 英文 | 代码前缀 | 含义 |
|---|---|---|---|
| 原始数据库 | Raw Store | `raw` | 信息侧 · 抓来未判断的原件 |
| 沙箱 | Sandbox | `sandbox` | 加工与待确认区（含 AI 自用笔记） |
| 主数据库 | Main DB | `main` | 事实侧 · 权威结构化数据 |
| 知识库 | Knowledge Base | `kb` | 语义侧 · 权威可检索资料 |
| 变更集 | Change Set | — | 一条提议内含的全部变更 |
| 判定对话 | Judge Conversation | — | 只回裁决与句柄的隔离对话 |

**建议在提案文档、README 与代码里统一使用这套词。** 现在"数据库"一词指三种不同东西，这种歧义最终会变成实现分歧。

## 10. 与当前代码的差距

四个区在代码里只实现了**两个半**：

| 区 | 现状 |
|---|---|
| 主数据库 | 有。SQLite 两张表（`tasks`、`schedule_blocks`），无课程、无校历事实、无迁移框架、无外键索引 |
| 沙箱 | 有雏形。`SANDBOX.md` 单文件分区，整节覆盖，无条目化、无时间戳、无来源 |
| 知识库 | 占位。`KeywordKnowledgeBase`，关键词打分，无分段、无向量、无元数据、无溯源 |
| 原始数据库 | **不存在**。门户抓取读完即丢，邮件未接入 |

因此"主动式信息管家"目前没有物理落点：没有原始区，就无法比较"昨天抓到的校历"和"今天抓到的"，也没有"这封邮件看过但没采纳"这个状态。

其余具体缺口（`level` 静默降级、提议卡片只有 `schedule.add` 可读、提议与沙箱分散在两个存储、`Approve` 非原子）见会话记录，未写入本文。
